# Shared Foundations

- **Search before duplicating.** Before adding infrastructure or a shared UI primitive, look for existing components and helpers that own the same behavior. Examples include atomic file writes, locks, time formatting, subprocess environment sanitization, bounds clamping, secret redaction, and async submission guards. A business helper can stay local until two or three concrete uses establish a common rule. When a second consumer depends on the same correctness, concurrency, lifecycle, or boundary guarantee, give both consumers one implementation at their narrowest common owner.
- **Give cross-boundary rules one owner.** For rules shared across processes, layers, or UI surfaces, designate the owner that derives the result and accepts changes. For example, let the window owner clamp requested bounds and publish the resulting geometry. Other surfaces send commands and render the owner's snapshot.
- **Finish the cutover.** When an engine, storage format, or component family supersedes an overlapping implementation, identify its callers and existing data. Migrate them, verify the behavior they rely on, and remove the superseded path once the cutover is complete.
- **Verify what crosses the boundary and what ships.** Exercise shared wire payloads in both runtimes with the same golden fixtures or contract tests, including serialization and parsing in each supported direction. Put smoke harnesses, diagnostic endpoints, and test backdoors behind compile-time features or build gates that exclude their code and registration from release builds.
